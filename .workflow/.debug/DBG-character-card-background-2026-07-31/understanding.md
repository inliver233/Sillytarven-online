# 角色卡与背景导入问题调查

**Session ID**: DBG-character-card-background-2026-07-31
**问题描述**: PNG 角色卡可能被误报为损坏；背景上传、视频转换、重命名及 CharX 内嵌背景存在异常。
**开始时间**: 2026-07-31 (Asia/Hong_Kong)

## 调查时间线

### Iteration 1 - 代码与本地数据核对

#### 已确认的事实

- 当前本地 `data/default-user/characters` 中只有 1 张角色卡，现有解析器可以正常读取，无法从本地现存卡直接复现线上用户的 PNG 失败。
- `/api/characters/import` 的异常分支仍以 HTTP 200 返回 `{ error: true }`，前端又把所有失败统一显示为“文件无效或损坏”。
- 角色导入的临时文件由多个格式解析函数分别删除，异常和若干提前返回路径不会清理。
- 拖放/替换只为 `charx`、`byaf` 使用扩展名兜底；PNG/JSON/YAML 在 MIME 为空或为 `application/octet-stream` 时会被拒绝。
- PNG 元数据读取总是优先选择第一个 `ccv3` 块，但没有验证其 Base64/JSON；一个损坏的 `ccv3` 会遮蔽同图中仍有效的 `chara` 块。
- 背景视频在缺少转换扩展时仍保留在 `FormData` 中并继续上传；服务端只按文件名保存且图库默认只枚举图片。
- 背景重命名没有同步全局设置、聊天锁定元数据和当前 CSS URL；新背景高亮把文件名直接拼入 CSS 选择器且假定节点存在。
- 聊天背景复制到全局背景时不检查上传结果，失败后仍会删除聊天元数据中的原项。
- CharX 背景被写入图库不会读取的 `characters/{显示名}/backgrounds`，且资产在角色 PNG 写入前落盘。

#### 当前结论

这些问题不是同一个单点故障，而是一组相互叠加的兼容性与失败处理缺陷。PNG 的“误报损坏”至少包含两类：服务端/代理/容量等非文件错误被错误翻译，以及 PNG 同时含有效 `chara` 和无效 `ccv3` 时解析器没有回退。

## 当前汇总理解

### 已知根因

1. HTTP 状态和前端提示丢失真实错误类别。
2. 文件类型过度依赖浏览器 MIME。
3. PNG 元数据候选没有逐个验证和回退。
4. 上传临时文件缺少路由级 `finally` 清理。
5. 背景操作缺少成功返回值和状态同步。
6. CharX 资产目标目录与前端可发现目录不一致，且写入顺序不具备失败安全性。

### 待验证

- 新 PNG 解析兼容逻辑对 `tEXt`、`zTXt`、`iTXt`、损坏优先候选和无元数据图片的行为。
- 背景内容嗅探与文件扩展规范化不会把合法 PNG/JPEG/WebP 误拒绝。
- CharX 背景导入后位于全局背景目录、URI 被重写且同名角色互不覆盖。

### Iteration 2 - 修复与验证

#### 已实施修复

- PNG 解析器现在会验证每个 `ccv3`/`chara` 候选，坏的 V3 不再遮蔽有效 V2，并支持 `tEXt`、`zTXt`、未压缩及压缩 `iTXt`。
- 无裁剪的 PNG 角色图不再经过 Jimp/WASM 重编码，直接保留像素数据并更新元数据，规避特定 PNG 解码器兼容问题。
- 角色导入异常改为真实的 400/415/500/507 状态和稳定错误码；日志包含格式、文件 basename、错误码和原始堆栈；临时文件由路由级 `finally` 统一删除。
- 拖放、替换和 URL 替换改为按扩展名准入并检查明确成功结果；前端分别提示卡片解析、格式、容量、鉴权、代理和网络错误。
- 背景上传会同时在浏览器和服务端检查文件签名，并根据实际内容规范化扩展名。无视频转换器时停止上传，转换结果也必须是有效 WebP。
- 背景重命名会同步全局设置、聊天锁定元数据、当前 CSS 和缩略图缓存；高亮不再拼接不安全选择器，也不再假定元素存在。
- 全局/聊天背景上传函数返回明确结果并显示成功/失败反馈；复制失败不再删除聊天背景元数据。
- CharX 背景改存全局背景目录，内嵌 URI 改写为可访问路径；背景、杂项和新导入精灵按内部卡名隔离。角色 PNG 首次写入成功后才持久化辅助资产。

#### 验证结果

- `npm run test:imports`: 14/14 通过。
- `npm run test:optimizations`: 3/3 通过。
- `npm run test:user-invitations`: 10/10 通过。
- 所有本次修改的 JS 文件定向 ESLint 通过，`node --check` 通过，`git diff --check` 通过。
- 全仓库 `npm run lint` 仍失败，但 370 个错误全部位于本任务未修改的既有文件；本次修改文件不在错误列表中。

## 最终结论

朋友的调查对核心故障点判断准确。当前数据没有提供可复现的持续线上失败样本，但代码中足以解释“正常 PNG 被报损坏”、假 HTTP 200、替换后继续旧聊天、视频孤立、重命名后背景消失及 CharX 背景不可见的确定缺陷，现均已有针对性修复和回归测试。
